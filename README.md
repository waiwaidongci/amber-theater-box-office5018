# 琥珀剧场｜票房计划与实收差异日报

`hxwl-solo2611-15` · 业务报表与贡献归因

结算组每天从排演预算表、剧场自营订单、合作平台结算及现场票窗交班单合并前一营业日数据。按原演出场次、渠道和票档对照计划净票房与净实收，供票务主管复核渠道退款、折扣和售票位。

## 模拟客户与工作流

江湾琥珀剧场票房结算组（6 人，单厅 420 座，演出日最多三场）

- 各渠道交班单口径不同，到账金额常和扣佣后的结算款混在一起。
- 日报只写票房差额，会上分不清是总票量下滑、低价档卖得多，还是同档折扣变大。
- 退款手工补录后，渠道小计与总表因重复取整对不上，需要拆单找差。

票务主管先派单给超退款率关注线的渠道。渠道经理复核净票房下滑达到关注线的场次和票档，对正向达到关注线的渠道保留当前售票位，核查余座后再安排加推。结算组把桥接、渠道处置和复算底稿随 CSV 发给售票组及财务。

## 业务模块

- 票房交班台账
- 营业日与桥接设置
- 净实收桥接与渠道处置
- 票房日报签收

## 计算口径

每个演出营业日、场次、渠道和票档占一行。计划净票房为计划票量乘以计划单价减计划退款，实际净实收为退款前实收减实退。两者均以佣金前口径计。退款按原票归集到演出营业日，按录入台账的快照复算，晚到退款须导入更新快照。固定桥接顺序为票量、组合、价格、退款。先以实际总票量替换计划总票量，沿用全剧场计划组合份额和基准单价；再切换为各明细的实际组合份额；接着替换为退款前实收；最后加入计划退款与实退的差异。计划票量为零且计划单价留空时，基准单价用该行实际票均实收。任一侧总票量为零时，两侧份额采用有票一侧。精确汇总后按显示粒度舍入，尾差用于对齐显示净差异。渠道贡献使用与全剧场相同的总票量和份额分母。此分解依赖替换顺序，用于对账与分派复核。

样例输入为 `琥珀剧场_票房交班_20261124.csv`，见 `backend/demo/sample.csv`。相同输入与参数复现相同结果。格式错误在导入时提示，样本量或业务约束不满足时在后台运行结果中提示。

## 重算一致性与版本发布

- **晚到退款**：退款仍按原演出营业日、场次、渠道和票档归集。每日计划物化时始终取最新数据批次，补录退款形成的新快照按原营业日参与重算；结果中保存该营业日的台账快照指纹与纳入行数。
- **幂等重跑**：运行以「营业日 + 台账快照校验和 + 计算参数」派生幂等键（`runs.idem_key`，数据库唯一约束兜底）。手动同批重跑、定时计划重复物化、两个并发提交以及断点恢复后的租约重领，都只会落到同一条运行，不重复生成结果；迟到的 worker 结果在落库前按租约代次丢弃。
- **一次性版本切换**：每个营业日在 `report_publications` 维护版本序列。重算未完成或未通过门控前，页面桥接与 CSV 下载继续返回当前生效旧版。发布前重新计算结果指纹，确认桥接、渠道处置、复算底稿同源且 CSV 底稿存在，全部一致后才在同一事务内激活新版并把旧版标记为 `superseded`；校验失败记为 `rejected` 且不切换。
- **旧任务不覆盖新版**：同营业日若已有由更新运行（更大运行 id）发布的生效版本，较早完成的旧运行发布会被拒绝。
- **签收保留**：历史版本的运行结果、复核结论、站内签收回执与导出 CSV 均随版本保留；同一运行至多一条回执，重跑不重复生成。
- 后端测试（无需 Docker，使用 SQLite 与 TestClient）：`cd backend && python3 -m unittest discover -s tests -v`。

## 一班如何使用

1. 11 月 24 日 08:35 结算员导入《琥珀剧场_票房交班_20261124.csv》。文件涵盖 11 月 22 日和 23 日，每日三场、三个渠道、两个票档，共 36 行。
2. 08:50 核对 11 月 23 日《雨夜邮局》《纸月》《西岸留声》的排演预算和渠道交班单，计划 412 张，实际出票 415 张。
3. 09:05 选定 11 月 23 日，按保留分运行，渠道净差异关注线为 1,000 元，退款率关注线为 10%。
4. 09:15 核对计划净票房 100,050.00 元，实际净实收 94,671.50 元，差额为 −5,378.50 元。实际退款比计划多 3,265.00 元。
5. 09:25 切换到元取整，核对全剧场桥接显示 1 元舍入尾差。另核对保留分的渠道量差与组合差各有 0.01 元汇总差。
6. 09:40 票务主管先查退款率 16.10% 的合作平台，安排票窗复核售票，剧场自营保留当前售票位。
7. 10:00 导出含桥接和复算底稿的 CSV，发送给剧场票务运营组和剧场财务结算组签收。

## 启动与本地开发

```sh
cp .env.example .env
docker compose up -d --build --wait
docker compose exec -T backend python -m scripts.seed_demo
```

停止本地服务可执行 `docker compose down`。仅清理演示数据时使用 `docker compose down -v --remove-orphans`。

浏览器 `http://127.0.0.1:18324`，API `http://127.0.0.1:19324`，数据库宿主端口 `17824`。

前端由 Nginx 提供原生 HTML/CSS/JS，并将 `/api/` 转发给 FastAPI。Python 3.11 Worker 使用 Redis 唤醒和 PostgreSQL 16 运行租约，生成的 CSV 由命名卷共享。可编辑 `frontend/src/pages`、`backend/src/services/analysis.py` 和 `backend/demo` 后执行 `docker compose up -d --build --wait`。Compose 默认映射到本机回环地址。更改 `.env` 可配置端口、数据库密码、JWT 密钥以及 `SEED_DEMO` 种子开关。演示凭据适用于本机模拟数据。

| 角色 | 账号 | 密码 | 工作内容 |
|---|---|---|---|
| 主管 | admin | admin-demo-2611 | 查看审计，复核运行，安排与停用分发计划 |
| 分析员 | analyst | analyst-demo-2611 | 导入 CSV、运行计算、下载结果 |
| 只读 | viewer | viewer-demo-2611 | 查看数据、结果和投递回执，下载 CSV |

角色、运行状态和复核状态在 `backend/src/constants/enums.py` 与 `frontend/src/constants/enums.js` 同步定义。角色参与登录、路由授权和工具栏控制。运行状态在 Worker、任务接口和结果页使用。复核状态在运行模型、复核接口和交付页使用。

核心实体为 CSV 数据批次、分析运行、分发计划及其投递回执。业务参数与真实模拟数据位于 `backend/demo/`。后端分为 routes、controllers、services、models、schemas 和中间件，前端分为 api、store、组件和业务页面。授权模式见 [LICENSE](LICENSE)。
